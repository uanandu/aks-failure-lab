P0Safety start here

Small changes that protect the page and saved progress before anything else changes.

  • Escape learner input. Notes and reflections are written back into innerHTML unescaped, so typing </textarea> breaks the page on the next render.
  • Export and import progress as JSON. Progress lives only in localStorage. Export also serves as a backup during the Phase 1 migration.
  • Version the saved state. Completed steps are saved by position (state.steps[labId][0]). Adding a step would shift every position and attach saved checkmarks to the wrong steps, so a version number and migration must exist first.
  • Baseline browser test. Checks so far cover HTML structure and JavaScript syntax only. Run keyboard-only and screen-reader passes now to have a baseline.

P1Foundation

Phases 3–5 add new fields to all 17 labs. Doing that by patching one large HTML string is error-prone.

  • Keep lab data in JSON with small render functions, built to the same single HTML file.
  • Give each step a stable ID (e.g. observe instead of 1) and migrate saved progress to it.
  • Store pacing plans as structured lab ranges rather than text such as "Labs 5–7", so Phase 5 can read them.

P2Correctness

Quick command fixes, so later guidance is written for labs that actually work.

LabProblemRecommended fix
7 · DNSThe "fault" step only starts a client Pod, so nothing actually fails.Start the client Pod with dnsPolicy: None and an unreachable nameserver (e.g. 192.0.2.10) so its lookups fail. This affects only that Pod and needs no NetworkPolicy engine; repair by recreating the Pod with the default DNS policy.
12 · LoadBalancerA default LoadBalancer Service in AKS is exposed through a public IP.Add service.beta.kubernetes.io/azure-load-balancer-internal: "true". The Service gets a private IP from the cluster's virtual network, so the lab still exercises Azure provisioning without internet exposure.
13 · HPAThe "repair" step only runs kubectl get hpa; nothing is fixed.Add a CPU request, e.g. kubectl set resources deployment/vote --requests=cpu=100m, then show the HPA target change from unknown to a percentage. Assumes the metrics API prerequisite is met.

P3Content largest learning gain

One pass through each lab, in this order, because hints point toward the expected evidence and must be written after it.

  • Prediction: one prompt before the fault, e.g. What will READY show for the vote Pods? The home page method starts with "predict," but no lab asks for a prediction yet.
  • Expected evidence: what should appear, such as an ErrImagePull or ImagePullBackOff reason, an empty EndpointSlice, or lastState.terminated.reason: OOMKilled.
  • Tiered hints, written by hand: where to look, what the clue means, then a worked diagnosis. Hints are currently generated from the reasoning bullets.
  • Labs 15–17 as scenarios: captured sample outputs to interpret and a written diagnosis to compare against, so "complete" has a clear meaning.
  • Manual capstone screen: the pacing plans mention a capstone, but the platform has none yet. A manual version can ship without the script.

P4Validation

check encodes the expected evidence from Phase 3, and chaos needs reliable start and reset for every lab.

./lab.sh start 4 # inject the fault ./lab.sh check 4 # verify recovery with kubectl jsonpath checks ./lab.sh reset 4 # restore the baseline ./lab.sh chaos # inject a hidden fault for the capstone

Proposed interface only; this script does not exist yet.

P5Experience

Depends only on Phase 1, so it can be built alongside Phases 2–4. Lowest learning value of the phases.

  • The selected pace currently changes only the schedule on the Progress page; the home page "Continue learning" card ignores it.
  • Replace that card with a pace-aware Today card, e.g. Day 3 of 7 · Labs 5–7 · continue Lab 6, and keep milestones and stats below it.

P6Portfolio
